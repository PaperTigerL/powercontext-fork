# gaode — 周边去哪儿：基于高德的地点推荐助手

本目录是 OceanBase 大赛「高德地图」生态赛题的参赛产物。赛题要求提交**一个 Skill 文件（`SKILL.md`）**，由评测平台加载后驱动 Agent 调用高德 MCP Server 完成「周边地点推荐」任务。

## 目录内容

| 文件 | 作用 | 是否被评测加载 |
|---|---|---|
| `SKILL.md` | 主交付物。Agent Skill 定义，包含 frontmatter 与完整任务流程 | 是，唯一被加载的文件 |
| `README.md` | 运行与验收说明、验证样例 | 否，供评审与自查 |
| `references/type-lexicon-and-units.md` | 支撑材料：地点类型词表与单位换算/阈值推导 | 否，仅作参考 |

`SKILL.md` 是自洽的：不读取本目录任何其他文件即可独立执行，`references/` 只是展开说明。

## 评测环境如何使用本文件

参赛者只需提供文件，运行链路完全由平台负责：

1. 平台统一提供 Agent 运行环境、执行模型与高德工具配置（含高德 API Key）。
2. 平台加载 `gaode/SKILL.md`，在单轮任务中让 Agent 按 Skill 的步骤执行一次「提出需求 → 查询高德 → 返回推荐」。
3. 平台自动采集高德工具调用记录，用它核对回答中的地点、位置与路线数据；参赛者无需导出 JSON、上传日志或编写测试脚本。
4. 平台不执行源码测试，也不需要源码、独立应用、测试报告或演示视频。

提交时按题面要求，基于 `2026-competition-ecosystem` 分支开发，相关项目资产放在本 `gaode/` 目录下；分支与 commit 由仓库维护者统一提交。

**不要在 Skill 或本目录内填写高德 API Key。**

### 关于高德工具名与参数

平台暴露的高德能力只有两项：地点搜索（按起点 + 关键词查附近地点）、步行路线规划（起点到候选地点的步行距离与预计耗时）。标准高德 MCP Server 中它们通常对应「周边 POI 搜索」与「步行路径规划」两类工具，参数语义为：中心点坐标 / 关键词 / 半径，以及起点坐标 / 终点坐标。

`SKILL.md` 中一律以「能力语义 + 参数语义」描述调用，并要求执行时先列出当前可用工具再按语义匹配。**具体工具名、参数名与返回字段以评测环境实际的 tool schema 为准**；`references/type-lexicon-and-units.md` 末尾附有标准实现的对照表，仅供核对。

## 评测会检查什么

评分方式为规则校验 + AI 评审，权重如下（数据真实性占 40%，是权重最高的一项）：

| 维度 | 权重 | 检查重点 |
|---|---|---|
| 数据真实性 | 40% | 回答中的地点名称、地址、位置、步行距离与时间是否与高德工具返回结果一致；未经数据支持的描述不得作为加分依据 |
| 需求满足 | 30% | 推荐数量上限、步行时间上限等明确条件是否被满足；只推荐步行时限内可达的地点 |
| 推荐合理性 | 20% | 筛选、排序、推荐理由是否有数据依据；无结果或信息缺失时是否被正确处理 |
| 表达清晰度 | 10% | 回答是否简洁、易懂、能让用户做决定 |

对应的硬性条件（`SKILL.md` 中以 R1–R9 标注）：

- 推荐最多 3 家，超时地点不得列入符合条件的结果。
- 步行时间与距离必须来自步行路线规划结果，禁止用直线距离替代。
- 结果不足要如实说明并给出放宽建议，不得凑数。
- 查询失败要说明服务异常，不得编造地点与路线。
- 安静程度、排队情况、营业状态等无依据信息标注「未核实」。
- 排序与「优先近一点」这类偏好要和路线数据一致。

无结果用例按「是否正确处理该情况」评分，推荐数量为零本身不扣分。

## 验证样例

以下 5 个样例覆盖题面列出的 4 类评测场景。「期望输出形态」描述回答应长什么样，不要求字面一致；具体地点、地址、距离与时间以评测环境高德实际返回为准。

### 样例 1 — 普通推荐

- 用户输入原文：`我在杭州龙翔桥地铁站（120.159, 30.256），想找一家咖啡馆，推荐最多 3 家。`
- 期望行为：调用地点搜索取回周边咖啡馆候选，对每个候选调用步行路线规划，按步行耗时升序取前 3 家；名称与地址照抄搜索结果。
- 期望输出形态：一行结论（起点 / 类型 / 步行上限 / 命中家数）+ 3 行表格（地点名称、地址、预计步行距离、预计步行时间、一句理由）+ 补充说明。表格行数恰为 3，距离与时间取自路线返回值。

### 样例 2 — 时间限制

- 用户输入原文：`我在北京三里屯，步行 10 分钟内能到哪些酒吧？最多 3 家。`
- 期望行为：以 10 分钟为硬上限，候选必须满足路线耗时 <= 600 秒才可入选；超时地点被剔除且不进入推荐表。
- 期望输出形态：表格中每一行的预计步行时间都不超过 10 分钟；结论行写明采用的是「步行 10 分钟内」这一条件。

### 样例 3 — 偏好排序

- 用户输入原文：`我在深圳南山科技园，附近找餐厅，步行 20 分钟内，推荐 3 家，优先近一点。`
- 期望行为：筛选后按步行耗时升序排列，耗时相同再按距离升序；在回答中说明「按步行耗时由近到远排列」。
- 期望输出形态：表格顺序与路线数据一致（耗时列自上而下不增），且有文字明确点出该排序依据。

### 样例 4 — 结果不足

- 用户输入原文：`我在成都春熙路，找书店，5 分钟步行可达，最多 2 家。`
- 期望行为：若最近的书店步行超过 5 分钟，则合格数为 0；如实说明检索到多少家、最近一家步行多久、超过上限多少，并给出放宽建议（放宽到 10 分钟或换起点）。
- 期望输出形态：不出现任何推荐行；一段说明 + 具体放宽建议，不编造书店名称、地址或距离。

### 样例 5 — 查询异常

- 用户输入原文：`我在武汉江汉路，帮我找附近的公园，步行 15 分钟内，3 家。`
- 期望行为：若地点搜索或步行路线规划工具报错、超时或返回空错误，先用相同参数重试一次；仍失败则说明服务异常。
- 期望输出形态：明确写出失败的是哪一项能力、错误摘要、重试情况，并说明没有可核对的数据、建议稍后重试；不给出任何地点、距离或时间。

### 补充检查点：无依据信息

任一样例中若用户追加询问「哪家更安静」「现在营业吗」「要排队吗」，回答必须标注「未核实」并说明工具未提供该数据，不得给出倾向性结论。这两项工具不返回评分、营业时间、人均等字段，因此这类信息一律不写。

## 自查方法

1. 打开 `SKILL.md`，确认 frontmatter 含 `name` 与 `description`，且 description 写明触发场景。
2. 逐条比对第 6 节「输出前自检清单」9 项，确认每个分支都有确定行为而不是模糊表述。
3. 用上面 5 个样例在本地或评测环境各跑一遍，检查输出的表格列、排序、单位换算与补充说明是否符合预期。
